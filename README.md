# Blueprint — Returns Resolution & Disposition Agent (AWS Bedrock AgentCore)

A post-purchase returns agent for a fictional outdoor retailer, **Cascade Outfitters**, built on **Amazon Bedrock AgentCore**. A return request becomes a governed case: eligibility is computed in code from a versioned policy pack, the model only drafts the customer-facing summary, and a figure verifier checks every amount and date in that draft against the computed decision before the summary may exist. The agent runs behind the AgentCore Runtime contract (`BedrockAgentCoreApp`, `POST /invocations`, `GET /ping`); Payments is wired as a port in R5 and the Gateway-shaped tool port in R6; Memory arrives as a port in R9, and Policy is mapped as a port that a later round wires in.

> **Work in progress** — this blueprint is built and passing its automated test and eval gates, but it has not yet finished hands-on local testing, and its companion blog post is not yet published. Expect changes. This notice comes off when both are done.

## Why this shape

AWS's own retail demos stop at the shopping cart. Post-purchase — returns, refunds, disposition — is where the money, the fraud and the policy risk actually sit, and it is open ground. This blueprint takes the position a bank-grade blueprint would: **the model talks, the code decides.** Eligibility, windows and exclusions are a policy pack evaluated by a deterministic engine; the model's one job in R1 is drafting the customer summary, and even that draft is verified figure by figure before it is stored.

## The laws (enforced in code)

1. **Eligibility is policy-as-data** — return windows, category exclusions and condition rules live in a versioned policy pack (`2026.10.1`); every decision records the pack version and the exact clauses that fired, including the one-day edge: a case requested on its window's last day passes, one day later fails, both graded.
2. **The model never computes money** — amounts are Decimal math in code from order + policy inputs; a figure verifier rejects any amount or date in a drafted summary that does not equal a computed value. From R2 the money of record is the **refund computation**: a content-addressed artefact whose every line carries its derivation, whose missing inputs are named `not_computable` rather than zero-filled, and whose stored figures are re-performed and tamper-checked by a verifier.
3. **Disposition is a matrix, not an opinion** — where a returned item goes is read off a versioned matrix (category × declared condition × item age band → disposition + resale channel), never improvised. A closed channel falls to the matrix's stated next cell with the reroute recorded on the decision; a fact set with no cell is `not_decidable` naming the missing dimension, never a default guess (R3).
4. **Fraud signals are scored in code** — *arrives in R4.*
5. **Refunds are dual-threshold and idempotent** — the pack's caps make a refund auto-approvable to $50, named-approver territory above it, and second-different-approver territory above $150; execution runs only through the payments port under a mandatory idempotency key, so a retried execution replays the original receipt and never double-refunds (R5).
6. **Carrier and label actions are tools, not prose** — labels, voids, tracking reads and pickups are named tools on a Gateway-shaped port, each call recorded with its inputs hash; a label's cost is reconciled against the refund computation on the artefact itself, and the mismatch is surfaced, never hidden (R6).
7. **Customer history is memory with limits** — memory holds event-shaped summaries of closed milestones (case decided, refund executed, case graded, fraud review closed), derived in code from the artefacts of record. Retrieval is by exact customer id only — there is no cross-customer surface anywhere — every read is written to an access log, and records past the pack's retention window are excluded and counted as expired, never silently deleted. Prior-case facts reach a customer only through the verified-messaging path, and the fraud engine scores from memory records to the same artefact it scores from the store (R9).
8. **Every customer-facing message is verified** — every message the system can emit is a typed template rendered from artefacts; the messaging verifier checks its figures, its stated facts and its content against the disclosure rules before it may be sent, and a message whose artefacts are superseded while it waits is withdrawn and re-drafted, never sent stale (R8).

## What R1 builds

- **Domain core** — return-case and order models (money = Decimal, one rounding rule); the Cascade Outfitters catalogue and orders are gold-by-construction: every order total is provable from catalogue prices in tests.
- **Eligibility engine v1** — evaluates the versioned policy pack: return windows by category (apparel/footwear 60 days, gear 90, electronics 30), excluded categories (gift cards, consumables), final-sale exclusion, customer-damage condition bar. Decisions carry the clause list an auditor would replay.
- **Intake port + reference feed** — eight planted requests against the seed orders, including the window edge pair (REQ-2003 inside by zero days, REQ-2004 outside by one). Ingestion is idempotent by request id.
- **Store port** — SQLite local default (`./data/returns.db`), Postgres dialect behind `DATABASE_URL`; numbered migrations with a runner (migration 0001); photo/receipt evidence behind an S3-shaped store port with SHA-256 recorded at put time and re-verified on read.
- **AgentCore Runtime shape** — the entrypoint uses the pinned `bedrock-agentcore` SDK's `BedrockAgentCoreApp` (see Honest status), plus a local harness (`make harness`) that starts the real server and drives `/ping` + `/invocations` over HTTP, and a demo (`make demo`) walking the eligible and ineligible edge cases end to end.
- **The agent step** — behind a model port (offline deterministic default; `hosted-bedrock` profile fail-closed until a model ARN is configured), the agent assembles the customer-facing return summary from the computed decision. The figure verifier runs over the final text: a wrong-figure probe fails in tests and in the eval gate.
- **API** — FastAPI surface for intake, cases, decisions and orders, sharing the one `CaseService` the Runtime entrypoint uses.

## What R2 adds — the refund computation engine

- **A Decimal ledger, line by line** — from the eligibility decision, the order as stored and the policy pack's refund schedule (restocking rates by declared condition: new-with-tags 0%, like-new 10%, used 20%; free return shipping for apparel and footwear; a flat $6.95 return-shipping deduction otherwise), the engine computes item credit, restocking fee and shipping deduction, each a named line carrying its derivation: pinned inputs, the rule, the policy reference.
- **Content-addressed and tamper-checked** — the computation's id hashes the decision + order fingerprints, pack version and engine version; `verify_computation` re-performs the arithmetic from the pinned inputs and detects any altered line, total or allocation (graded in tests and the eval gate).
- **Not computable is a stated state, never a zero** — a declared condition with no rate in the pack makes the fee `not_computable` naming the missing rate, the refund total stays open (`is_final` false) and the customer summary says exactly what it is waiting on. An order with no tender breakdown gets a final total but a named, missing tender allocation — where the money goes is not invented.
- **The summary quotes the computation** — the customer-facing refund is now the computed `refund_total` (the decision's `refund_due` remains the pre-fee eligibility figure), and the figure verifier's allowed universe extends to the computation's lines, totals and allocations: sayable figures are still a closed computed set.
- **Surfaces** — migration 0002 (`computations` table), `GET /cases/{id}/computation` (+ `/verify`, `GET /computations`), Runtime dispatch actions `get_computation` / `verify_computation`, and the demo prints the full breakdown. Hand-computed fixtures (multi-line order, fee-bearing categories, a shipping-deducted case) are exact to the cent in tests and evals.

## What R3 adds — the disposition matrix

- **A matrix, as data** — the disposition pack (`2026.10.1`) holds 36 primary cells over (category × declared condition × age band: fresh 0–30 days since delivery, season 31–90, aged 91+) plus stated fallback cells. Each cell names a disposition from a closed vocabulary — RESTOCK, REFURBISH, OUTLET, LIQUIDATE, RETURN_TO_VENDOR, RECYCLE, HOLD_FOR_INSPECTION — and the resale channel it flows through. New-with-tags resells at full price while current; fashion categories stale into the outlet with age while gear barely stales; used items are refurbished young and liquidated old; aged sealed electronics go back to the vendor.
- **Channel availability is data too, and reroutes are on the record** — a separate versioned channel table states which channels are open per category. The shipped table closes the apparel liquidator, so aged used apparel falls to its cell's stated next cell (RECYCLE via the recycler) and the decision records the hop: from-cell, the closed channel, to-cell. No decision ever lands on a non-primary cell without its reroute path attached.
- **Not decidable is a stated outcome** — an unknown category, a declared condition outside the matrix vocabulary, an age that bands nowhere, or a closed channel with no stated next cell returns a stored `not_decidable` artefact naming the missing dimension. There is no default disposition anywhere in the engine.
- **Content-addressed, tamper-checked, basis-labelled** — each decision is pinned to the case, the refund computation it was decided alongside, the matrix and channel-table versions (plus the table's content fingerprint) and the exact facts evaluated; `verify_disposition` re-performs the walk and detects any altered disposition, cell or reroute. Every R3 decision carries `basis: declared` — it rests on the customer's declared condition, and warehouse grading (R7) will supersede it with a new linked decision rather than editing it.
- **Holds name their unknowns** — used electronics are HOLD_FOR_INSPECTION at any young age, and the decision names exactly what inspection must establish (functional test result, data-wipe status) for a later round to consume.
- **Surfaces** — migration 0003 (`dispositions` table), `GET /cases/{id}/disposition` (+ `/verify`, `GET /dispositions`), matrix inspection reads (`GET /disposition/matrix`, `/disposition/matrix/cells/{cell_id}`, `/disposition/channels`), Runtime dispatch actions `get_disposition` / `verify_disposition` / `get_matrix` / `get_matrix_cell` / `get_channels` / `list_dispositions`, and the demo prints each case's disposition. Only eligible cases receive a decision; denied cases carry none. The eval gate sweeps all 36 rows against a hand-derived map with zero-tolerance counters for wrong dispositions, unexercised rows, undecidable-but-decided facts and silent reroutes.

## What R4 adds — the fraud scoring pack

- **A scoring pack, as data** — `fraud.py` holds the pack (`2026.10.1`, fail-closed loader): five deterministic signals computed in code from stored artefacts only, each recorded with its inputs and its Decimal contribution, summed under stated bands — CLEAR below 25, MONITOR from 25, FRAUD_REVIEW from 60. The signals: **return velocity** (prior cases in a 90-day window beyond a free allowance of 2, 8 points each, capped at 40); **serial-returner share** (share of the customer's orders returned, tiered to 35 — and only over at least 4 orders; below that the signal is `insufficient_data` and says so, because one order and one return is not a pattern); **wardrobing** (wear-category items declared new-with-tags after 21+ days of ownership, 12 points each, capped at 36); **weight mismatch** (carrier-scanned return weight against the product master's shipped weight — under half is the empty-box band at 30 points; nobody weighed the parcel means `not_computable` naming the missing input, never an assumed weight); **card churn** (distinct payment tenders across the customer's orders, tiered to 20; no tender breakdown on record is `insufficient_data` naming the same `payment_tender_breakdown` input the refund engine names).
- **Scores are content-addressed artefacts** — pinned to the case, the pack version and the exact input artefacts (customer's stored orders and cases, by id, under a content fingerprint). Re-scoring after new evidence writes a NEW artefact linked by `supersedes`; the old one stands unedited, and `verify_fraud_score` re-performs the arithmetic from the pinned inputs and names any tampered band, total or contribution.
- **FRAUD_REVIEW is a block, and the block has exactly one door** — a case in the `fraud_review` state keeps its disposition but its refund path is blocked (`assert_refund_path_open` is the guard the R5 gates must call). The block is lifted or confirmed only by a **named fraud-review decision act**: a reviewer of record, a coded outcome (`confirmed_fraud` / `cleared_with_reason`) and a reason code from the pack's vocabulary for that outcome. A confirmed finding is sticky across re-scoring; a clearance applies to the score it decided on, and the score artefact itself is never modified by the act — after a clearance the score still reads FRAUD_REVIEW at its computed total, with the case state carrying the decision.
- **Planted truth, graded exactly** — the seed history plants a serial returner (8 orders, all returned, 4 cards) whose live case scores exactly **95.00 → FRAUD_REVIEW**, and a wardrobing pattern scoring exactly **36.00 → MONITOR** with its share and churn signals honestly `insufficient_data`; every R1 feed customer scores 0.00 CLEAR. The eval gate adds zero-tolerance counters for band mismatches, block bypasses (tampered scores, off-menu outcomes, uncoded reasons, unnamed reviewers, second decisions), score irreproducibility and blocks lifted without a decision.
- **Surfaces** — migration 0004 (`fraud_scores`, `fraud_reviews`), every case carries its score + derived `fraud_state`; `GET /cases/{id}/fraud-score` (+ `/signals`, `/verify`), `POST /cases/{id}/fraud-score/rescore`, `GET /fraud-scores`, `GET /fraud/scoring-pack`, `POST /cases/{id}/fraud-review` (201; refusals 409, unnamed reviewer 422), Runtime dispatch actions `get_fraud_score` / `get_fraud_signals` / `verify_fraud_score` / `rescore_case` / `record_fraud_review` / `get_fraud_review` / `get_scoring_pack` / `list_fraud_scores`, and the demo walks the block and its lifting.

## What R5 adds — approval gates + the idempotent payments port

- **Thresholds are pack data** — the policy pack now carries the approval caps (`auto_approve_cap` $50.00, `dual_approve_cap` $150.00). A case's tier is computed from its final refund total: at or below the auto cap no named approval is needed; above it, one named approver; above the dual cap, a second approver who must be a **different person** — the same person approving twice is refused at record time, because one person twice is one approval.
- **An approval is a recorded act** — named approver, role, an explicit `as_of` date, and the exact computation it approves: the act pins the computation's id and total, so an approval taken against a superseded computation can never be counted for the current one (pinning a non-current computation is refused outright as stale). The customer who submitted a return cannot approve its refund, a denied or not-final computation has nothing approvable, and a case under a fraud hold refuses approvals through the R4 guard — an approver never overrides FRAUD_REVIEW.
- **Execution is precondition-checked, in code** — a current final computation, the fraud path open, a decided disposition, and the approval tier satisfied; every refusal names the missing piece. Money then moves only through the **payments port**, shaped on AgentCore Payments, under a mandatory idempotency key.
- **The payments double is a local stand-in — plainly.** The only implementation in this build is `LocalPaymentsDouble`, labelled as such in its code and on every receipt it produces (`local-double (AgentCore Payments stand-in)`). **It moves no real money.** In production, money movement rides the configured AgentCore Payments provider bound to the port; the double exists so the gates, the idempotency contract and the failure handling are built and graded offline.
- **Idempotency is structural, and graded by counting** — executing the same key twice returns the original receipt and the double's movement count stays at 1; a retry under a *different* key for an already-executed computation is refused as `duplicate_refund`. Receipts are stored artefacts (provider reference, amount, the computation's tender allocation, status), unique per computation and per key in the store.
- **Failures leave no partial state** — the double can be told to fail mid-execution per key; the service records a `failed` execution (transitions `requested → executing → failed`, the reason on the record), writes **no receipt**, and the case stays executable — the retry, same key or new, lands exactly one receipt.
- **Surfaces** — migration 0005 (`refund_approvals`, `refund_executions`, `refund_receipts`); `POST /cases/{id}/approvals` (201; refusals 409, unnamed approver 422), `GET /cases/{id}/approvals`, `GET /cases/{id}/approval-status`, `POST /cases/{id}/refund-executions` (201; gate refusals 409, provider failure 502), `GET /cases/{id}/receipt`, `GET /receipts`, `GET /cases/{id}/executions`; Runtime dispatch actions `record_approval` / `list_approvals` / `approval_status` / `execute_refund` / `get_receipt` / `list_receipts` / `list_executions`; the demo walks the full ladder — auto, single, dual, same-key replay and the duplicate-key refusal. The eval gate adds zero-tolerance counters for double refunds, unapproved executions, stale-pin approvals, fraud-blocked acts and partial receipts after failure.

## What R6 adds — carrier tools behind the gateway + the case timeline

- **One gateway, named tools, every call on the record** — `create_return_label`, `void_return_label`, `get_carrier_events` and `book_pickup` are defined once as MCP-style tool definitions (name, typed input schema, output description) and invoked only through the `ToolGateway`: it hashes the exact inputs, mints a call id, and records the call — success or refusal — against the case (tool, inputs hash, status, the artefact it produced or the refusal's reason). Artefacts a tool produces carry the call id that made them. Tool arguments arrive as JSON, so dates cross the boundary as ISO strings and are parsed in code; garbage refuses as a `ToolError`, never a guess.
- **Labels are artefacts with a schedule and a reconciliation** — issuance reads the service level off the policy pack (per-category service, a 2 kg freight threshold, per-level costs) and records the case's parcel weight from the product master — a missing weight or schedule entry refuses naming the input. The label cost is reconciled against the refund computation's return-shipping line on the label itself: `matched` when they agree, `retailer_absorbed` when the pack's free-return categories explain a zero deduction, `variance` with the exact figure standing whenever they differ (the planted electronics case: $8.50 charged, $6.95 deducted, $1.55 on the record), `not_reconcilable` naming why when there is nothing honest to reconcile against. A mismatch is a field on the record, never a footnote and never absorbed.
- **The carrier double is a local stand-in — plainly.** The only implementation in this build is `LocalCarrierDouble`, labelled as such in its code and on every artefact it touches (`local-double (carrier stand-in)`). **It moves no real parcels.** It is deterministic by construction: a label reference is derived from the exact issue inputs (replaying one issuance act returns the same reference; a fresh act after a void gets a fresh one), and its tracking script is tendered → in transit → received on stated days, read as of a date. In production, the retailer's real carrier integration binds behind the same port as an AgentCore Gateway target.
- **Idempotent issuance, void as a named act** — re-issuing for a case returns its active label: one artefact, one port-level issue, any number of recorded calls. Voiding is a recorded act by a named actor with a stated reason, producing a void artefact; the label then reads voided, a voided parcel is never reported received, and a fresh label may issue — linked to the voided one by `supersedes`, never replacing it in place. Labels refuse for ineligible cases and, through the R4 guard, for fraud-blocked cases: an approver or an operator never overrides FRAUD_REVIEW to get a parcel moving.
- **Pickups are for bulky categories only** — the pack flags the bulky categories (gear); `book_pickup` books against the case's active label in the pack's stated window, and refuses any other category naming the rule and the flagged set.
- **The summary gains the label, still verified** — once a label exists, the customer summary is re-composed through the same figure-verified flow with the label's reference, service level and cost appended; the figure verifier's universe extends to exactly one new sayable figure — the label cost, and only as the label artefact states it.
- **The case timeline is derived, never stored** — a read-only view assembles every artefact of record (intake, decision, computation, disposition, fraud score and reviews, labels, voids, pickups, carrier events, approvals, execution transitions, receipt) ordered by recorded timestamps, each entry carrying its source artefact id. Gaps are named, not papered over: a refund executed with no label, a ship-by date passed with no label, a label voided with no replacement, a fraud block awaiting its review decision. A denied case's timeline is short and gapless — nothing is expected of it.
- **Surfaces** — migration 0006 (`return_labels`, `label_voids`, `pickups`, `tool_calls`); `GET /tools`, `POST /cases/{id}/labels` (201; refusals 409, verification 422), `GET /cases/{id}/labels`, `GET /cases/{id}/label`, `GET /labels`, `POST /cases/{id}/labels/{label_id}/void` (201; unnamed actor 422), `GET /cases/{id}/labels/{label_id}/events`, `POST /cases/{id}/pickups` (201), `GET /cases/{id}/pickups`, `GET /cases/{id}/tool-calls`, `GET /cases/{id}/timeline`; Runtime dispatch actions `get_tool_definitions` / `invoke_tool` / `create_return_label` / `void_return_label` / `get_carrier_events` / `book_pickup` / `get_label` / `list_labels` / `list_pickups` / `list_tool_calls` / `get_timeline`; the demo walks issuance, idempotent re-issue, a void and superseding re-issue, a freight pickup for the tent, a refused footwear pickup, and a timeline with its gap named. The eval gate adds zero-tolerance counters for duplicate labels, labels accepted for ineligible or fraud-blocked cases, hidden cost mismatches, unnamed timeline gaps and non-bulky pickups.

## What R7 adds — warehouse grading + the supersession cascade

- **Receipt and grading are recorded acts** — a warehouse receipt exists only when the carrier's event script shows the case's parcel `received` as of the receipt date (the carrier's word governs, not the warehouse's say-so), naming the receiver; re-recording the same act replays it, a different act against a receipted label refuses. A grading report then records, under a named grader: the graded condition (the same vocabulary as the declared one), damage notes, the parcel's received weight, and — for held electronics — the functional test result and the data-wipe status. The receiver of a parcel cannot grade it: the same separation-of-duties pattern as the approval ladder, refused at record time.
- **A held case's grading must answer what the hold asked** — R3's HOLD_FOR_INSPECTION named its unknowns (`functional_test_result`, `data_wipe_status`); a grading report that does not record both refuses to finalise, naming the missing facts. When both are present, the hold resolves through a versioned inspection table in the grading pack (functional + verified wipe → REFURBISH through the store; failed test → RECYCLE through the recycler whatever the wipe; functional but unwiped → RECYCLE — a device that cannot be proven wiped is never resold), issued as a new disposition decision linked to the hold by `supersedes`.
- **The cascade runs in one stated order, each step a new artefact** — (1) graded condition ≠ declared → the disposition is superseded by a fresh matrix walk with `basis: graded`, re-checking channel routability for the graded season; (2) the refund is re-priced on the graded condition — a new computation supersedes the old, fee lines recording declared *and* graded conditions, and the report states the **delta** between the two totals explicitly (the planted boots, declared like-new: $130.50 → graded used: $116.00, delta −$14.50); (3) if money already moved, the delta becomes an **adjustment position** (below); (4) the customer summary is re-issued against the new computation, figure-verified as always, in the new figures only. Nothing is edited in place — the store now holds chains (migration 0007 drops the one-artefact-per-case uniqueness), heads resolve by following `supersedes`, and the eval gate compares the superseded payloads byte-for-byte after the cascade.
- **The executed-then-graded case is a position, never a silent absorption** — a negative delta after execution creates a `recovery_due` adjustment: amount, reason, the two computations it bridges, standing `open` as a recorded receivable with its own approval requirement noted — **no clawback execution exists** in this build, and nothing through the top-up path can move money for a recovery. A positive delta creates a `top_up_due` adjustment whose execution runs through the **same R5 gates**: approvals re-checked against the NEW computation (the old computation's approvals do not count), the fraud guard, and a namespaced idempotency domain (`topup:`) so a top-up key can never collide with a refund key; the top-up pays exactly the per-tender difference between the two computations. A plain re-execution of the new computation after the case already settled refuses, naming the settled receipt — the difference, and only the difference, can move, and only through the adjustment.
- **Grading feeds the fraud pack by re-score, never by edit** — the report's received weight supersedes the intake-scan weight for the weight-mismatch signal (the request artefact is untouched; the fact override is recorded in code), and when the graded condition is wildly worse than declared — two or more condition ranks — *and* the grader recorded wear evidence, the case re-scores through the existing R4 machinery: a new score artefact superseding the old (the planted jacket, declared new-with-tags, graded used with a 100 g weigh-in against an 820 g product: the empty-box band lands, 30.00 → MONITOR). A one-rank slip, or no wear evidence, raises nothing.
- **Honest edges stay honest** — grading a case to `damaged_by_customer` (a condition the matrix never priced) re-runs both walks and both say so: the computation is not final with the missing rate named, the disposition is `not_decidable` with the missing dimension named, no delta is claimed, and execution refuses on the non-final computation. Grading exactly what was declared changes nothing and records exactly that.
- **Surfaces** — migration 0007 (`warehouse_receipts`, `grading_reports`, `refund_adjustments`; computation/disposition chains); `POST /cases/{id}/warehouse-receipts` (201), `GET /cases/{id}/warehouse-receipts`, `POST /cases/{id}/grading-reports` (201; gate refusals 409, cascade figure-verification 422), `GET /cases/{id}/grading-reports`, `GET /cases/{id}/adjustments`, `POST /cases/{id}/top-up-executions` (201; gates 409, provider failure 502); Runtime dispatch actions `record_warehouse_receipt` / `list_warehouse_receipts` / `record_grading` / `list_grading_reports` / `list_adjustments` / `execute_top_up`; the timeline gains warehouse-receipt, grading and adjustment stages plus a named `warehouse_grading` gap; the demo walks the boots cascade into its recovery position and the lamp's hold resolving. The eval gate adds zero-tolerance counters for grading delta mismatches, in-place artefact edits, ungated top-ups, holds finalised without their inspection fields, and grading gate bypasses.

## What R8 adds — customer messaging: templates, the verifier, the lifecycle

- **Every message is a typed template** — six message types cover everything the system can say to a customer: the return summary (the R1 composer path, migrated onto the lifecycle with its text unchanged), label instructions, the grading-outcome notice (your refund changed because the graded condition differed), the fraud-review outcome notice (cleared / confirmed), the refund-executed notice, and the adjustment notice (top-up paid / recovery standing). Each renders from the case's artefacts of record through one `MessageFacts` assembly; a type whose artefacts do not exist yet refuses to draft, naming what is missing. Free-form model text is allowed only inside a stated note slot appended to a template — anything outside a template cannot be sent, because there is no other path to the messaging port.
- **The verifier checks three things, in code, before a message is sendable** — (1) **figures**: every amount, date and percentage equals a computed artefact value (the R1 figure check, generalised); (2) **facts**: every stated disposition and condition equals the artefacts of record — a draft claiming the held lamp "will be restocked" refuses, because the record says HOLD_FOR_INSPECTION; (3) **forbidden content**: the disclosure pack (`2026.10.1`, versioned data) bans the fraud pack's signal names, weights and thresholds, its review reason codes (derived from the scoring pack at check time, so the ban cannot drift from the pack), other customers' identifiers and case references, internal artefact ids beyond the case's own public references, and promises the policy pack does not make — the pack states no refund timing, so "within 3 business days" is unverifiable and refuses. A failing message is stored as `refused` with its violations listed — never sent, never silently fixed.
- **The fraud notice cannot leak, by construction** — its template has no slot for a signal, score, band, threshold or reason code: cleared reads "an additional review … the review is closed and your return will proceed as normal" with the refund figure from the computation; confirmed states the item amount and that no refund will be processed. The disclosure check then patrols the one free-form surface (the note slot) for the same vocabulary.
- **The lifecycle is recorded acts** — draft → verified → queued → sent, each transition on the artefact with its date and actor; sending runs through a messaging port with a labelled local double (production sending rides the configured provider). Send attempts are idempotent per message id: a repeat send returns the original delivery, the double's count does not move. A provider failure leaves the message queued, never half-sent.
- **Staleness is withdraw + re-draft, never send stale** — every message pins the artefacts it renders against (per type, by content fingerprint — the summary's pin covers the decision, the computation chain, the disposition chain and the label). Grading re-issues the summary, which withdraws any earlier unsent message of that type; any other supersession (a voided label under queued instructions) is caught at send time by the fingerprint: the send refuses, the message stands withdrawn, a replacement is drafted and verified against the current artefacts, and the refusal names it.
- **Surfaces** — migration 0008 (`customer_messages`); `GET /messaging/disclosure-pack`, `GET /messages`, `POST /cases/{id}/messages` (201; unknown case 404, undraftable 409), `GET /cases/{id}/messages`, `GET /cases/{id}/messages/refused`, `GET /cases/{id}/messages/{message_id}`, `POST …/verify` / `…/queue` / `…/send` (state refusals 409); Runtime dispatch actions `draft_message` / `verify_message` / `queue_message` / `send_message` / `get_message` / `list_messages` / `list_refused_messages` / `get_disclosure_pack`; the timeline gains message stages and a named `customer_message` gap for a message sitting queued. The demo walks the lifecycle, a refused inflated draft, and the stale-after-grading withdrawal. The eval gate adds zero-tolerance counters for unverified sends, stale sends, forbidden content sent, and figure/fact violations sent, over the four planted probes.

## What R9 adds — customer memory behind the AgentCore Memory port

- **A memory port shaped on AgentCore Memory — with a local double, plainly.** The `MemoryPort` surface is write / retrieve / retention-status over long-term records; the only implementation in this build is `LocalMemoryDouble`, a store-backed stand-in labelled on every record it writes (`local-double (AgentCore Memory stand-in)`). **It calls no real memory service.** In production, AgentCore Memory binds behind the same port; the record shape, the scoping and the retention rules are the blueprint's, and they are what the gates grade.
- **Records are event-shaped summaries, derived in code** — at each case milestone (case decided, refund executed, case graded, fraud review closed) the service derives one record from the artefacts of record: customer id, case id, the event type and its date, and the facts as recorded — the decided refund total and disposition, the executed amount, the graded condition and the refund delta, the fraud **band** and the review outcome. Score internals never enter a record — the band is the most a record ever says about fraud — and a decision record carries the exact scored fact set, so history can be re-scored from memory alone. Writes are idempotent per milestone and source artefact: replays and backfills never double a record, and a `sync` backfills milestones the live hooks predate (the planted closed history included).
- **Retrieval is limited, in structure** — the port's only read takes an exact customer id; there is no search, no filter, no cross-customer surface anywhere in the system, and the store enforces the predicate. Every retrieval — staff reads, the retention read, the fraud engine's, the message verifier's — is written to an **access log** (customer, purpose, actor, the exact record ids returned) before the records are handed over; a probe for a stranger returns nothing and the probe itself stands on the log.
- **Retention is pack data, and expiry is not deletion** — the memory pack (`2026.10.1`) states the window (730 days); a record's expiry is derived from its event date. Expired records are excluded from retrieval and from every consumer, and the retention read lists them as a tombstone count with their ids — the records themselves are never deleted by any code path in this build.
- **Two consumers, both pinned to the record** — (1) the R4 fraud engine gains a memory-sourced history path: its input is now an explicit provenance-tagged fact set (`history_source: store | memory` — a tag on the artefact, not an input to it), and a score computed from memory records is the *same content-addressed artefact* the store path produced, graded case by case; grading weigh-ins recorded in memory supersede intake weights exactly as they do from the store. (2) The agent's customer-context step: the R8 messaging verifier's figure universe extends to **the case's own customer's** memory records — a returning customer's earlier refund may be quoted in a new message only as memory records it, another customer's amount refuses even though it exists in memory, and an expired record's figure refuses too.
- **Surfaces** — migration 0009 (`memory_records`, `memory_access_log`); `GET /memory/config`, `POST /memory/sync`, `GET /memory/access-log`, `GET /customers/{id}/memory` (+ `/retention`, `/access-log`), `GET /cases/{id}/fraud-score/from-memory`; Runtime dispatch actions `get_memory_config` / `sync_memory` / `get_customer_memory` / `get_memory_retention` / `list_memory_access_log` / `score_case_from_memory`; the demo walks the memory records, the parity re-score and the retention read. The eval gate adds zero-tolerance counters for cross-customer leaks, memory/store score divergences, expired-record surfaces and unlogged retrievals.

## What R10 adds — the Postgres production profile + production smoke

- **The full suite runs on real PostgreSQL.** A test conftest redirects every sqlite-path `SqlStore` to a private schema on the test database (named by a hash of the path, so each test keeps its isolation and a "reopened" store lands on the same schema), and with `RETURNS_TEST_DATABASE_URL` set the whole suite — including the R1 dialect test that used to skip — runs against Postgres: 234 passed, 0 skipped. Without the variable the suite is byte-identical to before. Payloads stay JSON **text** in both dialects (never JSONB): the store contract is the exact JSON the domain layer wrote.
- **The eval gate runs every profile, with parity counters.** `evals/run_evals.py` now runs the full scenario body per store profile — in-memory and SQLite always, PostgreSQL when `DATABASE_URL` is set — and adds parity counters: every profile's zero-tolerance counters must agree, and the content-addressed artefact ids the planted work mints (receipts, fraud scores, computations, dispositions, labels, messages, memory records) must be **byte-identical across profiles**, or the gate fails. On the R10 run: all profiles GATE PASS, parity differences 0.
- **A production smoke (`make smoke`)** — `scripts/prod_smoke.py` drives the planted boots case through the whole lifecycle over HTTP: the Runtime entrypoint as a real subprocess server performs the intake, the operations API (same store) walks decide → compute → disposition → fraud score → approve → execute with an idempotent replay → label → carrier receipt → warehouse grading → adjustment → message lifecycle (draft → verified → queued → sent) → from-memory score parity, read back over **both** surfaces — 21 asserted steps, a printed ledger, nonzero exit on any failure. On Postgres it uses a private, run-scoped schema (R11); with no `DATABASE_URL` it falls back to a throwaway SQLite file and says so.
- **Two dialect defects found and fixed on the way.** (1) SQLite connections are thread-bound by default, so the API — which serves from a threadpool — 500'd on every store read under threaded serving while direct calls worked; the local profile now opens with `check_same_thread=False` (psycopg has no such restriction, which is why Postgres never showed it; a regression test serves the API on a SQLite store). (2) A `search_path` of `schema,public` lets an unmigrated private schema silently resolve its tables against an already-migrated public one — migrate() then reports nothing to do; the harness profiles use schema-only search paths so a missing table errors loudly instead of falling through.
- **Still true:** the Docker image build was not run (no daemon in the build sandbox); everything above ran against a real PostgreSQL 16 stood up in the sandbox, not a mock.

## What R11 adds — the Gateway port, generalized, + the Policy pack

- **Every tool-shaped operation now flows through the one gateway.** R6 built the gateway for the carrier tools; R11 completes the port: refund execution (R5's payments call — and the R7 top-up settlement with it) is the `execute_refund` tool, and the warehouse grading report is the `submit_grading_report` tool, the warehouse's callback. The gateway's implementation here is a **local double** for AgentCore Gateway, plainly labelled: it calls no real gateway and no real target. In production the port binds to AgentCore Gateway, whose MCP targets front the retailer's OMS, carrier, warehouse and payments integrations; the tool definitions, envelopes and invocation log do not change.
- **The invocation log is the audit surface.** Every invocation is recorded as an artefact: tool, case, **actor**, a digest of the exact arguments, a digest of the result, the timestamp, and the outcome — ok, the handler's named refusal, or a policy denial. Execution and grading artefacts carry their call's result reference, and the eval gate fails if a receipt or grading report of record has no corresponding gateway invocation beside it.
- **Refund money moves only against a prepared execution.** The service's execution flow keeps its gates (final computation, fraud path, disposition, approvals, duplicate checks) and prepares an execution record in `executing`; only then does it invoke the tool, whose handler verifies the prepared record — case, computation, status and amount — before the payments port is called. A bare tool call, however well-formed, moves nothing.
- **A Policy pack, as versioned data, evaluated before every invocation.** `gateway_policy.py` holds the pack (`2026.10.1`, fail-closed loader): named Cedar-shaped policies over an actor vocabulary (staff, returns_lead, warehouse, auditor, customer), evaluated **first-match deny, in pack order**, in code. It states: a customer never invokes a tool; carrier writes are staff work; tracking reads are open to staff, warehouse and auditor; the grading callback belongs to the warehouse; and — for the money tool — execution is denied when the case's fraud path is blocked, when the named computation is not the approved one, when it has already been executed under another key, when the amount argument exceeds the computed figure, and when the amount exceeds the invoking role's cap (staff and returns_lead capped at $500 in v1 — the design's Cedar example as a pack row). The carrier tools' own state gates (eligibility, the fraud hold) remain the handlers' named domain refusals, as defence in depth behind the pack. A policy change is a new pack version, never an edit; the pack is inspectable at `GET /gateway/policy-pack` and the Runtime's `get_gateway_policy_pack` action.
- **A denial is not an HTTP error.** In AgentCore, a Policy denial returns over a successful transport as a JSON-RPC error payload, code **-32002**. The double mirrors that shape exactly: the gateway records the invocation with status `denied` and the denying policy's id, the handler never runs, and the surfaces return the envelope — HTTP 200 with the JSON-RPC body — instead of an HTTP failure (API tool endpoints, the generic `POST /tools/{tool}/invoke`, and the Runtime's `invoke_tool`, which also takes an explicit `actor` now). The eval gate attempts every forbidden invocation in the pack and requires the named policy, the record, and zero side effects.
- **The Postgres harness is hermetic now.** The parent's R10 verification re-run against the already-used cluster failed — pytest reuses tmp-path names, so path-hashed schemas collided across runs (migration-ledger unique violations), and the eval factory's bare counter restarted at `eval_0`, leaking one run's memory records into the next. R11 gives every harness schema a **run-scoped suffix** (suite profile, R10 PG legs, R1 dialect leg, eval factory, production smoke — which no longer drops a schema to get a clean slate), and makes the migration ledger write conflict-tolerant, so `migrate()` on an already-migrated schema is a safe no-op in both dialects. Graded by running the PG suite and the PG eval profiles **twice** against the same cluster.

## What R12 adds — the model gateway + cost ledger

- **One gateway for every model-shaped call.** R1's model port is now a gateway (`model_gateway.py`): summary composition (all three composers) and the R8 message note slot route through it, and nothing else in the repo calls a model-shaped surface. Callers hand the service a composer as before — the service wraps it in the gateway's offline profile — or hand it a gateway directly.
- **Three profiles, one contract.** `offline` (the default): the deterministic composer, metered — its output is **byte-identical** to R1–R11 (graded against the bare port), its usage is the gateway's stated estimate over the inputs and the text, and its rate card is zero, so its recorded cost is $0.00. `bedrock`: a Bedrock Converse-shaped profile (request/response envelopes, model id as configuration). `nim`: an NVIDIA NIM-shaped profile (chat-completions envelopes, model id as configuration). Both hosted profiles are **stub-tested only** — no live AWS or NIM call is possible from this build environment and none is attempted; their transports are injectable callables, unbound by default.
- **Fail-closed, never fall back.** A configured-but-unreachable hosted profile — no transport bound, a transport error, no model id — raises and is recorded as `failed_closed`; the drafting surface reports the failure. The gateway never substitutes another profile's output, and never degrades a hosted profile to the offline composer.
- **Structured outputs only.** A profile's response enters the system only as a Pydantic-validated `DraftOutput`; hosted envelopes must carry a JSON object with the text. A malformed envelope or unvalidatable content is rejected, recorded as `rejected_invalid`, and never coerced. Structure is not truth: a well-formed hosted response stating a wrong figure still meets the figure verifier — graded with a stubbed Bedrock profile whose $999.99 summary is refused exactly like the offline composer's would be.
- **The cost ledger.** Every gateway call — composed, noted, rejected, refused, failed — is a `CostEntry` artefact (migration 0010): profile, model id, purpose, usage (the envelope's metering report for hosted profiles; the gateway's stated estimate, labelled as such, where no envelope exists), the unit prices pinned from a **versioned price pack** (`2026.10.1`), and the cost computed in code from them — never taken from a model's word. Unit prices are sub-cent rate-card data and quantise to the micro-unit; only costs are cents. `verify_cost_ledger` re-performs every entry's arithmetic; a tampered entry is detected. Reads: `GET /model/config`, `GET /model/cost-ledger`, `GET /cases/{id}/cost-ledger`, and the Runtime's `get_model_config` / `get_case_cost_ledger` / `get_cost_ledger` actions.
- **The runaway guard.** The price pack states a per-case call budget (40 in v1). A drafting call beyond a case's budget is refused with the budget named, and the refusal is recorded as `refused_budget` — refusals don't consume budget, and one case's exhaustion never touches another's. The demo walks the ledger the full case walk accumulates and fires the guard on a two-call budget.

## What R13 adds — the operations console

- **One static file, no build step** — `src/returns_resolution/console.html` is served by the API at `GET /console`: inline CSS and vanilla JavaScript, a light theme, and the Trida footer. It reads a stated operator name and role in the page — the same stated-actor convention the API already uses — and builds no login or identity system (that is R16).
- **Case board and detail** — cases are grouped by their furthest recorded lifecycle stage (intake, decided, computed, dispositioned, approved, executed, labelled, graded, closed), with counts and artefact figures only. A case detail walks the chain in workflow order: request, order and decision; refund computation lines; disposition chain; approvals, executions and receipts; labels, grading and adjustments; messages with verifier status; memory records; the case cost ledger; and the derived timeline with its named gaps.
- **Queues an operator can act on** — the review-hold queue carries the review act (named reviewer, coded outcome and reason) through the existing endpoint; the approvals queue shows computed amounts still missing a named approver and records approvals through the existing act; the recovery list shows open `recovery_due` positions. There is no other mutation surface in the console.
- **Money without new arithmetic** — executed refunds, executed top-ups and outstanding recoveries are sums over the receipt and adjustment artefacts the API returns, each total traceable to the rows listed beneath it. The footer states the rule on the page: the console sums artefact figures; it does not decide a case, price a refund or create a money artefact.
- **Gateway and policy, visible** — the invocation log (tool, case, actor, outcome, and the denying policy's id on a denial) and the current policy pack are rendered from the gateway reads.
- **Assessment detail stays out of the browser** — the console's dedicated read model carries an assessment's id, total, band and provenance, never its detailed payload. `make console-check` executes the console's own JavaScript against a seeded store and proves the rendered money totals equal the artefact sums, the review queue is exactly the open holds, and the static file carries none of the banned assessment-internal vocabulary.
